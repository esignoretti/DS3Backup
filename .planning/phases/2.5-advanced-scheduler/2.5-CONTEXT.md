# Phase 2.5: Advanced Scheduler - Context

**Gathered:** 2026-04-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Extend the existing cron-based scheduler from Phase 2 with resilience, observability, and control features. Adds retry logic, overlap prevention, missed-schedule handling, multi-schedule per job, and job concurrency policy. The daemon mode, HTTP API, system tray, and basic cron scheduling already exist in Phase 2 — this phase layers advanced capabilities on top without changing the existing CLI or API contracts.

</domain>

<decisions>
## Implementation Decisions

### Retry & Resilience
- **D-01:** Failed scheduled backups retry 3 total attempts (1 initial + 2 retries)
- **D-02:** Retry interval is fixed at 1 minute between attempts
- **D-03:** After final failure, escalate: set `job.LastError`, log the error, do NOT retry further
- **D-04:** Panic in scheduled job is recovered gracefully and treated as a failure (existing `RunJobAsync` panics are already recovered — this is consistent)

### Overlap Prevention
- **D-05:** If a backup takes longer than the cron interval, the overlapping scheduled occurrence is SKIPPED — next run happens at the next cron tick
- **D-06:** Per-job mutex/lock tracks whether a run is in progress before firing the next schedule

### Missed Schedule Catch-up
- **D-07:** On daemon restart, scheduler resumes from current time — missed schedules are logged but NOT executed
- **D-08:** The scheduler persists its last-checkpoint time so it can log which schedules were missed on restart

### Job Concurrency Policy
- **D-09:** Different jobs run fully in parallel (independent goroutines) — no global serialization
- **D-10:** A single job cannot overlap with itself (enforced by D-05/D-06)

### Multi-Schedule Per Job
- **D-11:** Jobs support a list of cron expressions instead of a single one
- **D-12:** Each cron expression in the list fires the same backup pipeline — no per-expression options (no backup type, no mode flags per schedule)
- **D-13:** The `models.BackupJob.CronExpr` field becomes a slice `CronExprs []string`; the existing single-string field is replaced (breaking change to model — planner must handle migration)

### The Agent's Discretion
- Webhook / notification on completion (not discussed — deferred)
- Backup window constraints (not discussed — deferred)
- Exact mechanism for persisting scheduler checkpoint time for missed-schedule logging
- Dashboard/API display of multiple cron expressions per job
- The `NextRun` API response field when a job has multiple schedules (show nearest upcoming, or list all)

</decisions>

<specifics>
## Specific Ideas

- "Attempt three times, and after it show an error and write it to the logs" — retry should be transparent to the user until final failure
- Overlap skip should log: "Skipping scheduled run for job X — previous run still in progress"

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `internal/scheduler/` package — Full scheduler, BackupJobRunner, ScheduleManager to extend
- `robfig/cron/v3` — Existing cron parser in `scheduler.go`, supports all standard expressions
- `internal/cli/daemon.go` — Daemon lifecycle (`runDaemon`, `stopDaemon`, `statusDaemon`) that wraps scheduler start/stop

### Established Patterns
- Constructor injection: all scheduler components use `New*` constructors (e.g., `NewScheduler`, `NewBackupJobRunner`, `NewScheduleManager`) — retry/concurrency wrappers follow same pattern
- Async execution: `RunJobAsync` uses `go func()` with recover — pattern extends to retry wrapper
- Config persistence: post-run config saving via `cfg.SaveConfig()` in `BackupJobRunner.RunJob` — retry mechanism should only save on final success or final failure

### Integration Points
- `ScheduleManager` (`internal/scheduler/job.go`) is the integration point between config and scheduler — update `LoadAllSchedules`, `EnableJobSchedule`, `DisableJobSchedule`, `RescheduleJob` for multi-schedule and retry
- `BackupJobRunner.RunJobAsync` wraps `RunJob` in goroutine with recover — wrap with retry logic at this layer

</code_context>

<deferred>
## Deferred Ideas

- **Webhook / Notification on completion** — Call URL or script on backup completion/failure. Enables Slack, email, custom integrations. Belongs in a future phase.
- **Backup Window Constraints** — Restrict when backups can run (e.g., 'only between 2-6 AM') as a gating condition. Belongs in a future phase.
- **Schedule Calendar Preview API** — Endpoint to preview upcoming N runs. Not discussed — low priority.
- **Configurable backup type per multiple schedule** — E.g., hourly = incremental, weekly = full. Not needed for now; multiple expressions all fire the same pipeline.

</deferred>
