# Phase 3.3: Tray Icon & Menu Improvements - Research

**Researched:** 2026-05-07
**Domain:** macOS System Tray / Desktop Notifications
**Confidence:** HIGH

## Summary

The system tray implementation has six categories of gaps: (1) a broken platform-detection gate that prevents the tray from ever starting on macOS, (2) a static 16x16 blue icon with no status-awareness, (3) per-job menu items created once and never updated, (4) no last-run-result visibility per job, (5) unreliable notifications via `osascript`, and (6) no progress or animation feedback while backups are running.

**Primary recommendation:** Fix the DISPLAY gate bug (tray never starts on macOS), replace the static icon with multiple 22x22 status PNGs (idle/running/failed/completed), implement menu-item dynamic updating per refresh cycle, and replace `osascript` with `terminal-notifier` as an optional dependency. The `getlantern/systray` library fully supports runtime `SetIcon()` calls — confirmed by reading its source code and the macOS native Objective-C implementation.

### Platform Detection Bug (Critical)

The daemon startup at `internal/cli/daemon.go` line 237 contains:

```go
runtime.GOOS == "darwin" && os.Getenv("DISPLAY") != ""
```

**`DISPLAY` is an X11 environment variable.** macOS does not set it by default — it is only present when running XQuartz (an optional X11 server). This means the tray **never starts** on macOS. The condition should be:

```go
runtime.GOOS == "darwin" && (os.Getenv("DISPLAY") != "" || os.Getenv("TERM_PROGRAM") != "")
```

Or simply gate on "no graphical session detected" rather than `DISPLAY`:

```go
runtime.GOOS == "darwin" && os.Getenv("SSH_CONNECTION") == ""
```

## Architecture Patterns

### System Architecture Diagram (Tray Component)

```
+------------------+       poll /api/v1/status (5s)       +------------------+
|                  | ──────────────────────────────────▶   |                  |
|  TrayApp         |                                      |  Daemon API      |
|  (onReady loop)  | ◀──────────────────────────────────  |  (port 8099)     |
|                  |       JSON StatusResponse             |                  |
+------------------+                                      +------------------+
       |                                                         |
       | systray.SetIcon()                                       | runBackupForDaemon()
       | systray.SetTitle()                                      | calls tray.Notify*
       | MenuItem.SetTitle()                                     |
       v                                                         v
+------------------+                                      +------------------+
|  macOS            |                                      |  BackupEngine    |
|  NSStatusBar      |                                      |  (has progressCb |
|  (menu bar icon)  |                                      |   callback)     |
+------------------+                                      +------------------+
```

Data flow:
1. Tray's `refreshStatusLoop` polls API every 5s via HTTP GET `/api/v1/status`
2. API returns `StatusResponse` with `Running`, `SchedulerRunning`, `ScheduledJobs`, `Uptime`
3. Menu items updated via `MenuItem.SetTitle()`
4. Per-job status fetched from `/api/v1/jobs` → `BackupJobWithStatus[]`
5. Icon changed via `systray.SetIcon()` based on aggregate state

**Missing flow today:** The `BackupEngine.RunBackup()` accepts a `progressCb func(BackupProgress)` callback parameter, but `runBackupForDaemon()` passes `nil`. If wired, the tray could show real-time progress per job.

### Pattern 1: Dynamic Icon Changes at Runtime
**What:** `systray.SetIcon()` can be called at any time from any goroutine to change the tray icon. The underlying implementation on macOS calls `statusItem.button.image = image` on the main thread via `performSelectorOnMainThread`.
**When to use:** On each status poll cycle, determine aggregate state (any running? any failed?) and call `systray.SetIcon()` with the appropriate icon bytes.
**Source:** `systray_darwin.m` lines `setIcon:` → `statusItem.button.image = image` [VERIFIED: reading systray source at github.com/getlantern/systray]

```go
// Called from refreshStatus() when aggregate state changes
func setTrayIconForState(state TrayState) {
    switch state {
    case StateIdle:
        systray.SetIcon(idleIconData)
        systray.SetTooltip("DS3 Backup Daemon - Idle")
    case StateRunning:
        systray.SetIcon(runningIconData)
        systray.SetTooltip("DS3 Backup Daemon - Backup in progress...")
    case StateFailed:
        systray.SetIcon(failedIconData)
        systray.SetTooltip("DS3 Backup Daemon - Last backup failed")
    case StateCompleted:
        systray.SetIcon(completedIconData)
        systray.SetTooltip("DS3 Backup Daemon - Backup complete")
    }
}
```

### Pattern 2: Dynamic Menu Item Updates
**What:** `MenuItem.SetTitle()` can update any menu item's text after creation; `MenuItem.SetTooltip()` updates the tooltip; `MenuItem.Enable()`/`MenuItem.Disable()` toggles interactivity.
**When to use:** On each status poll cycle, update job sub-menu item titles to include status indicators.
**Source:** `systray.go` lines 159-169 [VERIFIED: reading systray source]

**Anti-Pattern to Avoid:** Creating new menu items on each poll cycle (causes menu flicker / item accumulation). Instead, store `*systray.MenuItem` references in a map (`t.jobRunItems`) and call `SetTitle()` to update existing items.

### Pattern 3: Terminal-Notifier with Osascript Fallback
**What:** Use `terminal-notifier` when installed (via `exec.LookPath`), fall back to `osascript` otherwise.
**When to use:** For all desktop notification calls.
**Source:** terminal-notifier GitHub docs [CITED: github.com/julienXX/terminal-notifier]

```go
func sendMacOSNotification(title, message string) error {
    // Prefer terminal-notifier if available
    if path, err := exec.LookPath("terminal-notifier"); err == nil {
        cmd := exec.Command(path, "-title", title, "-message", message, "-group", "ds3backup")
        return cmd.Run()
    }
    // Fallback: osascript
    script := fmt.Sprintf(`display notification "%s" with title "%s"`, message, title)
    return exec.Command("osascript", "-e", script).Run()
}
```

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Generate PNG icons at runtime | Byte-slice construction | Pre-made 22x22 PNGs embedded as Go byte slices | Icons are static assets; build once with any image editor |
| macOS Notification Center integration | Direct ObjC/CGO bridge | `terminal-notifier` CLI (optional) + `osascript` fallback | UserNotifications framework requires `.app` bundle; daemon is a CLI binary |
| Template icon adaptation (dark/light mode) | Custom icon for each mode | `systray.SetTemplateIcon()` | Native macOS support via template image flag — call `systray.SetTemplateIcon(templateBytes, regularBytes)` |
| Animated tray icon | Frame-by-frame timer | "Static icon reflecting last-known state" icon | Menu bar animation is not standard for backup tools; status change is sufficient |

**Key insight:** The `getlantern/systray` library already provides all the primitives needed — `SetIcon()`, `SetTitle()`, `MenuItem.SetTitle()`, `MenuItem.Enable/Disable`, `MenuItem.Check/Uncheck`. The gaps are in how these are called, not in missing library capability. Every feature improvement listed here is achievable with the v1.2.2 API.

## Common Pitfalls

### Pitfall 1: DISPLAY Gate Blocks Tray on macOS
**What goes wrong:** Tray never starts because `os.Getenv("DISPLAY")` is empty on standard macOS.
**Why it happens:** `DISPLAY` is an X11 environment variable. macOS native GUI does not use X11 — only the optional XQuartz server sets it.
**How to avoid:** Check `os.Getenv("SSH_CONNECTION") == ""` or `os.Getenv("TERM_PROGRAM") != ""` to detect a local GUI session.
**Warning signs:** Tray logs "No display available, running in headless mode" even when running in a local Terminal window on macOS.

### Pitfall 2: osascript Notification Display Flakiness
**What goes wrong:** `display notification` with `osascript` often fails silently or displays notifications inconsistently — especially when the daemon runs as a background process without a Terminal window.
**Why it happens:** `osascript` requires a running `NotificationCenter` service and may be sandboxed for background processes.
**How to avoid:** Use `terminal-notifier` as primary (provides reliable Notification Center delivery), fall back to `osascript`.
**Warning signs:** `NotifyBackupComplete` / `NotifyBackupFailed` are called but no notification bubble appears.

### Pitfall 3: Menu Items Never Update After First Poll
**What goes wrong:** `ensureJobBackupItems()` is guarded by `if len(t.jobRunItems) > 0 { return }`, so job items are created once and never refreshed. If a job is added or removed after tray start, the menu is stale.
**How to avoid:** Move the guard to check job list length vs. `t.jobRunItems` keys, and call `MenuItem.SetTitle()` on existing items in each poll cycle.
**Warning signs:** Job menu items show old names or missing new jobs.

### Pitfall 4: Icon Not Refreshable (Myth)
**What goes wrong:** Developers assume the icon can only be set once in `onReady()`.
**Why it happens:** Many GUI libraries require icon setup at init time.
**How to avoid:** `systray.SetIcon()` works at any time — confirmed by reading the macOS implementation which calls `statusItem.button.image = image` each time.
**Source:** `systray_darwin.m` lines `setIcon:` [VERIFIED]

### Pitfall 5: Multiple `AddSeparator()` Calls on Refresh
**What goes wrong:** If job items are re-created (not just re-titled), each cycle adds more separators.
**How to avoid:** Never re-create job items — always update in place via `SetTitle()`.

## Code Examples

### Determining Aggregate Tray State from Status

```go
// Source: Derived from existing refreshStatus() pattern
// Assumes per-job running status is available
func (t *TrayApp) determineState(jobs []api.BackupJobWithStatus) TrayState {
    anyRunning := false
    anyFailed := false
    for _, job := range jobs {
        // Job's last run could have failed (LastError non-empty)
        // or a run could be in progress (would need API field)
        if job.LastError != "" {
            anyFailed = true
        }
    }
    // Could also check if scheduler/dashboard reports any active runner
    if anyRunning {
        return StateRunning
    }
    if anyFailed {
        return StateFailed
    }
    return StateIdle
}
```

### Dynamic Per-Job Menu Item Update

```go
// In refreshStatus(), after querying jobs:
for _, job := range jobs {
    item, exists := t.jobRunItems[job.ID]
    if !exists {
        // Add new job item
        item = systray.AddMenuItem(
            fmt.Sprintf("▶ Backup: %s", job.Name),
            fmt.Sprintf("Trigger backup for %s", job.Name),
        )
        t.jobRunItems[job.ID] = item
        // Set up click handler
    }
    // Update title with status indicators
    title := fmt.Sprintf("▶ Backup: %s", job.Name)
    if job.LastError != "" {
        title = fmt.Sprintf("⚠ Backup: %s (failed: %s)", job.Name, job.LastError)
        item.SetTitle(title)
        continue
    }
    if job.LastRun != nil {
        title = fmt.Sprintf("✓ Backup: %s (last: %s)", job.Name, job.LastRun.Format("15:04"))
    }
    item.SetTitle(title)
}
```

### Adding "Last Result" Sub-Items Per Job

```go
// Called once per job at creation time, then updated via SetTitle:
func (t *TrayApp) addJobInfoSubItems(jobID string, parentItem *systray.MenuItem) {
    lastRunItem := parentItem.AddSubMenuItem("Last run: --", "Last backup time")
    resultItem := parentItem.AddSubMenuItem("Result: --", "Last backup result")

    t.menuItems["lastRun_"+jobID] = &menuItem{item: lastRunItem}
    t.menuItems["result_"+jobID] = &menuItem{item: resultItem}

    // Store for later updates
    t.jobInfoItems[jobID] = &jobInfoItems{lastRun: lastRunItem, result: resultItem}
}
```

## Open Questions

1. **Can we detect which jobs are currently running from the API?**
   - What we know: `BackupJobWithStatus` has `LastError` but no `IsRunning` field. `BackupJob.RunInProgress` exists but is `json:"-"` (not serialized).
   - What's unclear: Whether we should add a `running` field to the API response, or rely on the scheduler's in-memory state.
   - Recommendation: Add a `running` field to `BackupJobWithStatus` (serialize `RunInProgress`). Alternatively, expose current-run info at a new endpoint like `/api/v1/backup/running`.

2. **Should the tray support Linux/Wayland?**
   - What we know: `getlantern/systray` supports Linux via GTK3 + AppIndicator. The daemon already has `runtime.GOOS == "darwin"` guard.
   - What's unclear: What the user's deployment target is.
   - Recommendation: Keep the macOS-only guard for now. If Linux support is needed, add it in a follow-up phase (requires gcc + libgtk-3-dev + libayatana-appindicator3-dev).

3. **Should we add icon animation (spinning/flashing) during backup?**
   - What we know: `systray.SetIcon()` is goroutine-safe and can be called rapidly.
   - What's unclear: Whether animated tray icons are UX-appropriate for backup tools.
   - Recommendation: Don't animate. Arq, Backblaze, and Time Machine all use static status icons with menu text updates. Animation is distracting in the menu bar.

4. **Should we embed PNG icons as Go `embed` resources?**
   - What we know: Current approach uses hardcoded byte slices. `go:embed` is supported in Go 1.16+ (project uses 1.25.0).
   - What's unclear: Whether `.png` files at a known path are easier to maintain than generated byte arrays.
   - Recommendation: Use `go:embed` with `.png` files in `internal/tray/icons/` — cleaner, easier to regenerate icons.
