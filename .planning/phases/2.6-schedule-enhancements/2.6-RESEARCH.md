## User Constraints (from CONTEXT.md)

### Locked Decisions (Phase 2.5, still apply)
- **D-01:** Failed scheduled backups retry 3 total attempts (1 initial + 2 retries)
- **D-02:** Retry interval is fixed at 1 minute between attempts *(Note: this is a locked decision from 2.5. Adding exponential backoff as an option would modify this.)*

### Pattern 1: Interval Schedule Implementation

**What:** Support "every 6h" alongside cron expressions. Two approaches:

**Approach A (Recommended): Use robfig/cron `@every` syntax.**
The `robfig/cron` v3 library already supports `@every 6h` syntax [ASSUMED: based on common knowledge of the library]. Convert user-friendly "6h", "30m" to `@every 6h`, `@every 30m` format and register with the existing cron instance. This requires zero additional infrastructure.

**Approach B: Standalone interval timer goroutine.**
Run a separate goroutine per interval-scheduled job that ticks on the specified interval. More control (can fire immediately, can skip overlapping, etc.) but duplicates cron's scheduling logic.

**Recommendation:** Approach A — it reuses the existing `cron.Cron` instance and `entries` map. The cron `@every` syntax already supports intervals and coexists with standard cron expressions. If `@every` does not exist or has issues, fall back to Approach B.

**Interval parsing flow:**
```
User input "6h" or "30m"
  → time.ParseDuration("6h") [VERIFIED: stdlib, always available]
  → Format as "@every 6h"
  → ScheduleJob with ["@every 6h"] alongside cron expressions
```

**When to use:** User specifies `--interval 6h` instead of `--cron "0 */6 * * *"`.

### Pattern 2: Blackout Window Evaluation

**What:** A blackout window is a time range (start time + end time, in local time) during which scheduled backups are not executed.

```go
type BlackoutWindow struct {
    Start     string `json:"start"`     // "02:00" (2 AM)
    End       string `json:"end"`       // "06:00" (6 AM)
    Timezone  string `json:"timezone"`  // "Local" or "UTC" or IANA name
}
```

**Evaluation in `BackupJobRunner.RunJob`:**
```
1. Before proceeding with backup execution
2. Get current time in job's configured timezone
3. For each blackout window, check if current time falls within [Start, End)
4. If within any blackout window:
   a. Log: "Skipping scheduled run for job X — inside blackout window 02:00-06:00"
   b. Return without executing (same as overlap skip pattern)
```

**Key design decision:** Blackout windows affect ALL triggered runs (both cron and interval). They gate the execution, not the scheduling. The cron tick still fires; the gate just blocks execution.

### Pattern 3: Schedule Timeout

**What:** Maximum duration a single scheduled run is allowed to take. After timeout, the run is cancelled and marked as failed.

```go
// In BackupJob struct:
ScheduleTimeout time.Duration `json:"scheduleTimeout,omitempty"` // e.g., 2 * time.Hour
```

**Implementation in `BackupJobRunner.RunJob`:**
```
1. If job.ScheduleTimeout > 0:
   a. Create context with timeout: ctx, cancel := context.WithTimeout(context.Background(), job.ScheduleTimeout)
   b. Pass ctx to runBackupFn (which passes it through the backup pipeline)
   c. defer cancel()
2. If the backup pipeline respects context cancellation, it will abort when timeout fires
3. On timeout: treat as a failure (same as retryable error)
```

**Important caveat:** The backup pipeline must actually check `ctx.Done()`. From examining the code, `runBackupForDaemon` in `internal/cli/daemon.go` calls `engine.RunBackup(job, false, nil)` — the backup engine needs to propagate context for timeout to be effective.

### Pattern 4: Exponential Backoff

**What:** Replace the fixed 1-minute retry interval with calculated backoff.

**From decisions D-01/D-02:** 3 total attempts, fixed 1-minute interval.

**Proposed enhancement:** Keep 3 total attempts but use exponential backoff:
- Attempt 1 → immediate
- Attempt 2 → 1 minute wait (base)  
- Attempt 3 → 2 minute wait (base × 2)

```go
backoff := time.Duration(math.Pow(2, float64(attempt-1))) * time.Minute
// attempt 1 → 1 minute, attempt 2 → 2 minutes
```

**Configurable option:**
```go
// In BackupJob struct:
RetryBackoffBase time.Duration `json:"retryBackoffBase,omitempty"` // default 1 minute
RetryMaxAttempts int           `json:"retryMaxAttempts,omitempty"` // default 3
```

### Pattern 5: Missed Schedule Catch-Up

**What:** On daemon restart, execute a limited number of missed scheduled runs instead of just logging them.

**From D-07:** Currently logs missed schedules but does NOT execute them.

**Proposed modification to D-07:**
- Keep logging as-is
- Add optional catch-up: execute up to N most-recently-missed runs per job
- N is configurable (default 0 = no catch-up, preserves D-07 behavior)
- Maximum N recommended: 3 (prevents catch-up flood on long outages)

```go
// In DaemonConfig:
MaxCatchUpRuns int `json:"maxCatchUpRuns,omitempty"` // 0 = disabled (D-07 default)
```

### Anti-Patterns to Avoid
- **Mixing interval and cron in the same field:** Keep `CronExprs []string`. If the user provides an interval expression, convert it to `@every` format and store it in `CronExprs`. Do NOT create a separate `IntervalExpr` field that duplicates scheduling logic.
- **Blocking in blackout evaluation:** The blackout check must be fast (time comparison only). Never make network calls or blocking I/O in the gate.
- **Using `context.Background()` for timeout:** Always derive from a cancel-capable context so both timeout AND daemon shutdown can cancel a long-running backup.
- **Overlapping blackout windows:** Multiple blackout windows per job should be OR'd (any window active = blocked). Document this clearly.

| Problem | Don't Build | Use Instead | Why |

**Key insight:** This entire phase requires zero new external dependencies. Go's standard library `time`, `context`, and `math` packages provide everything needed. The existing `robfig/cron` dependency already supports `@every` syntax for interval scheduling.

## Common Pitfalls

### Pitfall 1: Interval vs Cron Confusion
**What goes wrong:** User specifies both `--cron "0 2 * * *"` and `--interval "6h"`, and the job fires twice as often as expected.
**Why it happens:** Both are stored in `CronExprs` — the interval gets converted to `@every 6h`, which fires independently of the cron expression.
**How to avoid:** Document that `CronExprs` can contain a mix of cron expressions and `@every` directives. If both `--cron` and `--interval` are provided on the CLI, they are AND-ed (all entries fire independently). If the user wants only one, they should use only one flag.
**Warning signs:** `NextRun` field shows two upcoming runs close together.

### Pitfall 2: Blackout Window Timezone Mismatch
**What goes wrong:** A blackout window "02:00-06:00" is evaluated against UTC when the user intended local time.
**Why it happens:** Default timezone handling is ambiguous.
**How to avoid:** Default to `"Local"` (the machine's timezone) and make the timezone field explicit. Use `time.LoadLocation` for IANA names.
**Warning signs:** Backups run during what the user perceives as "nighttime."

### Pitfall 3: Timeout Killing the Process
**What goes wrong:** A backup timeout fires, the context is cancelled, but the backup pipeline doesn't check `ctx.Done()`, so the goroutine continues running.
**Why it happens:** The backup pipeline has a context parameter but may not check it in long-running loops (e.g., S3 uploads).
**How to avoid:** After the timeout goroutine fires, the backup finishes naturally in the background. Log a warning. The `RunJob` function returns, and the result is never saved (no LastError update for the timed-out run). This is acceptable but documented.
**Warning signs:** Backup takes much longer than the timeout, then the next scheduled run is skipped (overlap prevention).

### Pitfall 4: Catch-Up Flood
**What goes wrong:** Daemon offline for 72 hours with hourly backups. On restart, catch-up tries to execute 72 missed runs.
**Why it happens:** No limit on catch-up.
**How to avoid:** Hard cap at `MaxCatchUpRuns` (default 0, max 3). Log: "Job X missed ~72 runs. Catch-up limited to 3."
**Warning signs:** After restart, CPU spikes and multiple backups run simultaneously.

### Pitfall 5: Exponential Backoff and Overlap Prevention Conflict
**What goes wrong:** Retry with backoff keeps the per-job mutex locked during the backoff sleep, preventing the next cron tick from running.
**Why it happens:** The mutex is held for the entire `RunJob` duration (including retry waits).
**How to avoid:** This is actually the CORRECT behavior — the mutex prevents overlap. Document that during retry-with-backoff, subsequent scheduled occurrences are skipped (same as if the backup was still running).
**Warning signs:** "Skipping scheduled run for job X — previous run still in progress" messages during retry window.

### Interval Conversion (scheduler/interval.go)
```go
// IntervalParser converts user-friendly interval strings ("6h", "30m") to
// robfig/cron @every format for scheduling.
package scheduler

import (
    "fmt"
    "time"
)

// ParseInterval converts "6h", "30m", "2h45m" to "@every 6h" format.
// Returns empty string if the input is a valid cron expression (not an interval).
func ParseInterval(s string) (string, error) {
    // Try to parse as duration first
    d, err := time.ParseDuration(s)
    if err != nil {
        // Not an interval — might be a cron expression, return as-is
        return "", nil
    }
    if d < time.Minute {
        return "", fmt.Errorf("interval %q is too short (minimum 1 minute)", s)
    }
    return fmt.Sprintf("@every %s", d.String()), nil
}
```

### Exponential Backoff Calculation (scheduler/backoff.go)
```go
const (
    DefaultBackoffBase = 1 * time.Minute
    DefaultMaxAttempts = 3
)

// RetryBackoff returns the wait duration for the given attempt number (0-indexed).
// attempt 0 → no wait (first attempt), attempt 1 → base, attempt 2 → 2*base, etc.
func RetryBackoff(attempt int, base time.Duration) time.Duration {
    if attempt <= 0 {
        return 0
    }
    return time.Duration(math.Pow(2, float64(attempt-1))) * base
}
```

## Open Questions

1. **Should `CronExprs` store `@every 6h` strings, or should there be a separate `IntervalExpr` field?**
   - What we know: `CronExprs` already exists as `[]string`. cron `@every` syntax is a valid cron expression format.
   - What's unclear: Whether mixing cron expressions and `@every` strings in the same field is confusing to users.
   - Recommendation: Store both in `CronExprs` — the cron library treats `@every` as a first-class expression. This keeps the model simple (one field) and maintains backward compatibility. The CLI can make it look like separate concepts via `--cron` and `--interval` flags.

2. **Should retry exponential backoff replace or supplement the fixed 1-minute interval (D-02)?**
   - What we know: D-02 is a locked decision from 2.5. Changing it requires user confirmation.
   - What's unclear: Whether the user wants to replace D-02 or add exponential backoff as a configurable option.
   - Recommendation: Add as a configurable option (`RetryBackoffBase` on `BackupJob`). Default `0` = use fixed 1-minute (preserves D-02). Non-zero = use exponential backoff with that base.

3. **Should blackout windows be deny-list (prohibit runs in a range) or allow-list (only allow runs in a range)?**
   - What we know: The CONTEXT.md deferred "Backup Window Constraints" (allow-list). "Blackout Windows" implies deny-list.
   - What's unclear: Which semantics the user expects.
   - Recommendation: Implement deny-list (blackout). It's composable: "only allow between 2-6 AM" = blackout *outside* 2-6 AM. Simpler to explain and implement. Flag as question for discuss-phase.

4. **Should catch-up apply to ALL jobs or only jobs with explicit `MaxCatchUpRuns > 0`?**
   - What we know: D-07 says "missed schedules are logged but NOT executed." Adding catch-up modifies D-07.
   - What's unclear: Whether the user wants catch-up as opt-in (default 0 = D-07 behavior) or opt-out.
   - Recommendation: Opt-in. Default `MaxCatchUpRuns = 0` preserves D-07. User explicitly sets `--catch-up 3` to enable.

## Risk Assessment

| Feature | Risk Level | Primary Risk | Mitigation |
|---------|-----------|--------------|------------|
| Interval scheduling | **LOW** | `@every` syntax not supported by cron library | Fallback to standalone timer goroutine (adds ~50 LOC) |
| Blackout windows | **LOW** | Timezone handling edge cases | Use `time.LoadLocation` from stdlib; fallback to Local |
| Schedule timeout | **MEDIUM** | Backup pipeline ignores context cancellation | Timeout at least prevents retry loop from continuing; document as best-effort |
| Exponential backoff | **LOW** | Conflict with D-02 (fixed interval) | Make configurable with 0-default preserving D-02 behavior |
| Missed catch-up | **MEDIUM** | Catch-up flood from long outage | Hard cap at `MaxCatchUpRuns` (max 3); require opt-in |
| CLI/API surface | **LOW** | Too many new flags | Group flags logically under `job schedule` subcommand |

### Overall Phase Risk: **LOW**
- No new external dependencies
- All features are backward-compatible (default values preserve existing behavior)
- All features are additive (no existing code removed or refactored)
- All features are independently testable (no complex integration scenarios)
- Already-existing features (concurrent run prevention) correctly identified and excluded

## Key Design Decisions to Make

1. **Where to store interval expressions:** In `CronExprs` as `@every 6h` (recommended) or in a new field
2. **Blackout semantics:** Deny-list (recommended) vs. allow-list
3. **Retry backoff:** Configurable option replacing or supplementing D-02
4. **Catch-up:** Opt-in default 0 (recommended) vs. opt-out
5. **Timeout granularity:** Per-job (recommended) vs. global
6. **Catch-up concurrency:** Sequential (recommended) vs. parallel
